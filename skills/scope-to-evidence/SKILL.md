# Scope to Evidence

将“需求承诺了什么”与“当前证据能证明什么”逐项对照。默认只读审查；输出报告不等于修改实现、执行上线或签署验收。按用户语言交付，不绑定行业或办公平台。

## 输入与范围

先检查用户指定的需求、方案、验收材料、仓库及已有报告。记录审查日期、源文件版本／日期、仓库路径和 Git revision；工作区有变更时说明审查是否包含这些变更，不将 HEAD 视为整个工作区的标识。

- 明确审查对象与基线：哪个版本的哪些需求、哪些组件、需要判断实现还是验收就绪。
- 缺少材料时先完成有依据的部分。只有缺失信息会改变需求解释或结论时才提问；无法取得的证据标为“无法验证”，不能标“缺失”。
- 相互冲突的材料进入冲突表。较新不自动代表已批准；不得用代码现状反向改写需求，也不得把过期版本的承诺混进当前基线。
- 远端材料使用可用且已授权的连接方式；读取失败保留资源名称与失败原因。不要擅自换用另一个平台或账号。

## 审查方法

1. **提取可验证条目。** 给每项需求稳定 ID，并保留原文定位。拆开可以独立成功或失败的行为；不要把建议扩写成强制需求。将含糊表述转为“建议验收条件”，与来源明确的条件分开。
2. **定向找证据。** 从需求关键词、页面、接口、配置或数据入口开始，沿实际调用路径检查有关环节。仅在需求涉及权限、租户隔离、导出、写回等时检查对应完整路径，不扩大成仓库全量安全扫描。
3. **记录证据与局限。** 为证据分配 ID，记录位置、版本、支持的具体主张及不能证明的部分。引用采用可打开的路径＋行号，或文档章节／页码；不得虚构行号和链接。测试文件存在和测试执行通过是不同证据。
4. **逐项下结论。** 使用下方状态，按 [判定规则](references/evidence-rules.md) 处理 Mock、历史日志、负面证据与验收。必须为“已实现”和“缺失”给出足够的依据；不确定时缩小主张。
5. **交付可执行报告。** 使用 [报告模板](templates/review-report.md)，可以按任务规模删去不适用的节。每项缺口给出影响、最小下一步验证／修复建议与通过条件。没有明确负责人或时间就写“待指定”，不自行承诺。

## 状态必须分开

**实现判断：** `已实现` / `部分实现` / `缺失` / `无法验证`。

**证据维度分别记录：** 源码检查、运行验证、部署状态、验收状态。它们不是一个可以互相替代的完成分数。源码可支持“已实现（仅源码检查）”，不能支持“线上可用”或“客户已验收”。样例运行必须标明 Mock／真实连接和环境。

不要仅按行数计算“项目完成率”。用户需要汇总时，说明分母、拆分方式和未知项；按实现状态与运行验证分别汇总，不把需求条目覆盖率叫作验收通过率。

## 验证与交付

对静态审查，不强制运行项目。已授权且环境允许时执行相关、可控的本地验证；运行前识别真实网络、费用、数据写入和破坏性副作用，沿用用户已有授权。不能运行时仍交付静态结论及明确的未验证项，不用 Mock 替代真实集成证明。

交付前检查：每条范围内需求都有结论或未决原因；结论可回到原需求和证据；重大冲突未被隐藏；没有把缺访问权限当成未实现；摘要与矩阵一致。保存报告到用户指定位置，未指定时选项目内合适的文档／输出目录并保留已有版本。最终给出文件链接、关键缺口和实际验证边界。

示例：需要理解输出粒度时看 [脱敏示例报告](examples/review-report.md)。维护者的行为测试在 [evals/README.md](evals/README.md)，普通审查无需加载。
